# Google Chat ETL

:::warning[Off by default]
Google Chat ETL does nothing unless the workflow host sees
`GOOGLE_CHAT_ETL_ENABLED=true`. Enable it only after choosing the exact app
spaces and delegated DM subjects whose data Centaur may retain.
:::

Google Chat ETL is separate from live bot delivery. The `google_chat_sync`
workflow reads Chat history into Postgres and writes each thread it reads as a
custom document in [company context](/operate/company-context), where the
company-context service embeds it and makes it searchable. The
`google_chat_retention` workflow deletes only Centaur-derived rows; it never
mutates Google Chat.

## Authentication and scope

Shared-space sync uses the Chat app credential with:

- `chat.bot`;
- administrator-approved `chat.app.messages.readonly`.

The app can enumerate spaces where it is a formal member. Use explicit
`spaceIds` for readable spaces that `spaces.list` does not return.

Private DM sync is a separate opt-in path. It impersonates only the Workspace
users listed in `dmSync.subjects` and requests these read-only DWD scopes:

- `chat.messages.readonly`;
- `chat.spaces.readonly`;
- `chat.memberships.readonly`;
- `chat.messages.reactions.readonly`.

The sandbox sends only the requested subject, operation, resource name, and
bounded pagination through `WorkflowContext` to api-rs. api-rs accepts an exact
lowercase subject from `dmSync.subjects`, validates the resource and operation,
and forwards the read to googlechatbot. googlechatbot alone holds the service
account and mints delegated tokens for this path. Shared-space app reads use
iron-proxy's separate service-account grant. Never add the service-account JSON to
`SESSION_SANDBOX_PASSTHROUGH_ENV`; subjects remain explicit and are never
discovered from a global Workspace directory.

## Configure

Both workflows are always scheduled: `google_chat_sync` every 4 hours and
`google_chat_retention` every hour. Workflow discovery runs without deployment
environment, so the schedules cannot depend on it. Each run reads its settings
when it starts and returns `skipped` when it is disabled. To keep the workflows
from running at all, leave them out of the workflow allowlist
(`WORKFLOW_ENABLE_MODE=allowlist`).

| Environment variable | Default | Effect |
| --- | --- | --- |
| `GOOGLE_CHAT_ETL_ENABLED` | `false` | Enables `google_chat_sync`. |
| `GOOGLE_CHAT_INCLUDE_SPACE_TYPES` | `SPACE` | Comma-separated shared space types. `DIRECT_MESSAGE` is ignored here and uses the owner-scoped path below. |
| `GOOGLE_CHAT_MAX_PAGES_PER_RUN` | `0` | Per-space page budget. `0` drains to completion; a positive value persists a continuation for later runs. |
| `GOOGLE_CHAT_SPACE_IDS` | empty | Comma-separated pinned space IDs or resource names. When set, only these spaces are synced. |
| `GOOGLE_CHAT_DWD_DM_SYNC_ENABLED` | `false` | Enables delegated, owner-scoped DM enumeration. |
| `GOOGLE_CHAT_DWD_DM_SUBJECTS` | empty | Exact comma-separated Workspace users permitted as DWD subjects. |
| `GOOGLE_CHAT_RETENTION_ENABLED` | `true` | Enables scheduled retention runs. |
| `GOOGLE_CHAT_RETENTION_DAYS` | `0` | TTL for Google Chat rows and documents. `0` disables deletion. |
| `GOOGLE_CHAT_RETENTION_BATCH_LIMIT` | `1000` | Maximum rows deleted from each target per run. |

The chart has no values for these settings. Set them in `apiRs.extraEnv` and
list their names in `SESSION_SANDBOX_PASSTHROUGH_ENV` so api-rs passes them to
workflow-host sandboxes. api-rs also passes the workflow host its
`DATABASE_URL` (or `WORKFLOW_HOST_DATABASE_URL` when set); the sync writes
company-context documents through it, so it must point at the database the
company-context service uses, and company context must be enabled.

## Continuation and incremental reads

Each `(owner_email, space_id)` checkpoint records a create-time watermark,
last error, and optional `nextPageToken` plus the exact filter that produced it.
A bounded read resumes the same page chain on the next run instead of advancing
the watermark past unread history.

Scheduled runs deliberately rescan history without a `createTime` filter so
old messages edited later converge; Chat has no `updateTime` list filter.
Explicit manual `since` runs retain a bounded create-time filter. Every message
scan requests the official `showDeleted=true` option. Tombstones contain no
content, so the ETL deletes the corresponding retained message, attachment, and
reaction rows for both shared spaces and owner-scoped DMs. A failure updates the
affected checkpoint without advancing its successful
watermark; other spaces continue and the run becomes `partial_failed` when
appropriate.

## Stored data and privacy

| Table | Contents |
| --- | --- |
| `google_chat_sync_spaces` | Space metadata, owner identity, canonical member IDs, and display names. |
| `google_chat_sync_messages` | Message/thread identity, sender, normalized text, timestamps, raw payload, and error state. |
| `google_chat_sync_attachments` | Official message-qualified attachment metadata and raw payload. Google does not expose attachment text or byte size in this resource. |
| `google_chat_sync_reactions` | Message-qualified reaction, user, Unicode/custom emoji, and raw payload. |
| `google_chat_sync_checkpoints` | Watermarks, resumable continuations, and last error. |
| `google_chat_sync_runs` | Workflow run status, counts, successful/failed scopes, and safe error text. |

Shared spaces use an empty `owner_email`. Delegated DMs use the normalized,
explicitly allowlisted DWD subject as `owner_email`. Memberships contribute
canonical user IDs and display names; Google Chat's `User` resource does not
expose email.

## Company-context documents

After paging a space, the sync renders every thread it touched (a message
upserted or a tombstone deleted) as one row of
`company_context_system.custom_documents` with `source = 'google-chat'`:

| Column | Value |
| --- | --- |
| `external_id` | `spaces/<space>/threads/<thread>`; DM threads are prefixed with the owner, `<owner_email>/spaces/<space>/threads/<thread>`. |
| `title` | The first message's text, up to 80 characters, or `Chat thread in <space>`. |
| `body` | The space, start time, participants, and every message with its sender, time, attachment names, and reactions. Bodies are cut at the table's 1,000,000-byte limit. |
| `occurred_at` | The first message's create time. |
| `readers` | See below. |
| `metadata` | Space ID, name, and type, thread ID, message count, participants, and for DMs `owner_email`. |

A thread whose stored messages were all deleted has its row deleted. Rows are
only rewritten when their content or readers change.

Company-context queries run as the session's principal, and a Google Chat
session's principal is its space, `gchat-space-<slug of the space ID>`. So:

- a shared-space thread has `readers = {principal:gchat-space-<slug>}` and is
  visible only from sessions in that space;
- a DM-sync thread is visible only from the owner's DMs with the bot: its
  readers are `principal:gchat-space-<slug>` for every session whose thread
  key is a Chat space and whose metadata records a verified `DIRECT_MESSAGE`
  request from the owner's email, the same metadata api-rs uses to label the
  owner's `gchat_dm` principal. An owner who has never messaged the bot has no
  readers, and the thread is hidden until a later sync touches it.

Attachments are not indexed separately. Google does not expose attachment
text, so the sync stores names, content types, and raw metadata only, and the
thread document lists the names. It does not follow URLs or download files.

## Run and verify manually

Use a reachable api-rs endpoint and an authorized bearer with the `workflows_write` capability.
Loopback and in-pod requests still require authentication. Set
`CENTAUR_API_AUTH_HEADER_FILE` to a protected file containing the Authorization
header; keep the credential out of shell arguments and output. Run the SQL
examples through your configured read-only PostgreSQL connection.

Start a bounded sync in the selected environment:

```bash
curl --fail-with-body -sS -X POST \
  "${CENTAUR_API_URL%/}/api/workflows/runs" \
  --header "@${CENTAUR_API_AUTH_HEADER_FILE}" \
  -H 'Content-Type: application/json' \
  -d '{
    "workflow_name": "google_chat_sync",
    "input": {"max_pages_per_run": 2, "metadata": {"reason": "manual_check"}},
    "eager_start": true
  }' | jq
```

Inspect checkpoints and continuation pressure:

```sql
SELECT owner_email = '' AS shared, space_id, watermark_time,
          continuation_token <> '' AS continuing,
          continuation_started_at, last_error
     FROM google_chat_sync_checkpoints
    ORDER BY updated_at DESC
    LIMIT 100;
```

Check data and document counts without printing message or DM content:

```sql
SELECT owner_email = '' AS shared, count(*)
     FROM google_chat_sync_messages
    GROUP BY shared
    ORDER BY shared DESC;

SELECT metadata ? 'owner_email' AS dm, readers = '{}' AS hidden, count(*)
     FROM company_context_system.custom_documents
    WHERE source = 'google-chat'
    GROUP BY dm, hidden;
```

Verify that every shared-space document is readable only from its own space:

```sql
SELECT count(*)
     FROM company_context_system.custom_documents
    WHERE source = 'google-chat'
      AND NOT metadata ? 'owner_email'
      AND readers <> ARRAY['principal:gchat-space-' ||
          trim(both '-' from regexp_replace(lower(metadata->>'space_id'), '[^a-z0-9]+', '-', 'g'))];
```

The expected count is zero. Also query company context from two DM sessions
with the bot owned by different allowlisted subjects: each must find its own
DM threads and not the other's.

## Retention

Start with a count-only run:

```bash
curl --fail-with-body -sS -X POST \
  "${CENTAUR_API_URL%/}/api/workflows/runs" \
  --header "@${CENTAUR_API_AUTH_HEADER_FILE}" \
  -H 'Content-Type: application/json' \
  -d '{
    "workflow_name":"google_chat_retention",
    "input":{"retention_days":30,"mode":"count","batch_limit":1000},
    "eager_start":true
  }' | jq
```

`dry_run` and `count` report bounded candidate counts. `delete` removes, in
dependency order, `google-chat` documents whose thread started before the
cutoff, attachments, reactions,
messages, completed checkpoints, empty spaces, and terminal runs. Active
continuations and running workflow records are not retention candidates.

Only switch to `delete` after reviewing the result. Each run deletes at most
`batch_limit` rows from each target, so repeated scheduled runs drain a large
backlog without one unbounded transaction.

## Metrics and alerts

The workflow exports bounded-label metrics for:

- run status and duration;
- Chat API operations and rate limits;
- messages, files, and reactions processed;
- failed spaces and failure reason;
- continuation age and watermark lag;
- last failure time;
- retention items by mode and type.

Alert on a growing `google_chat_etl_continuation_age_seconds`, stale
`google_chat_etl_watermark_lag_seconds`, a non-zero failed-space gauge, or a
recent failure timestamp. Correlate those metrics with
`google_chat_sync_runs` and checkpoint errors without logging OAuth tokens or
message bodies.

## Live acceptance gate

Before calling the ETL production-ready, verify in a non-production Workspace:

1. an app-member shared space and a pinned shared space converge across a
   positive page budget without duplicates or skipped history;
2. card-only text, attachments, and reactions appear in the expected rows and
   in the space's company-context documents, which other spaces cannot find;
3. two allowlisted DM subjects each find only their own DM threads from their
   DMs with the bot;
4. a 429 and a permission error leave resumable checkpoints and safe,
   credential-free errors;
5. retention `count` and `delete` remove only expired Centaur rows and never
   mutate Workspace messages.

Save redacted workflow IDs, checkpoint output, metrics, and reader checks in
the parity verification ledger. It records successful shared/DM ingestion on
older releases; deletion convergence, reader scoping, retention, and a same-release rerun
remain separate gates.

## Disable or roll back

Set `GOOGLE_CHAT_ETL_ENABLED=false` and `GOOGLE_CHAT_DWD_DM_SYNC_ENABLED=false`,
then deploy. Existing rows and documents remain available until retention or an
explicit reviewed cleanup removes them; deleting the `google-chat` rows from
`company_context_system.custom_documents` removes them from search at once. Revoke
the DWD grants if DM ingestion is being retired. Application rollback should
leave the additive ETL schema in place until no deployed version references it.

See [Google Chat](/reference/google-chat) for ingress, permissions, delegated
operations, files, durable delivery, and the complete live smoke matrix.
