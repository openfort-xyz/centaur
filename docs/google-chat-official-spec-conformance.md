# Google Chat official-spec conformance ledger

**Audit date:** 2026-08-14

**Normative baseline:** Google Chat REST discovery revision **20260809**, cross-checked against the current Google Workspace developer reference pages linked below.

**Scope:** the current local Centaur branch, including Google Chat ingress, REST/OAuth, rendering, ETL, and the internal authorization brokers.

This is a traceability ledger, not a claim that the current branch has run in production. The read-only VPS inspection found an older deployment, image `sha-980e5e3b…`. It supplies useful legacy evidence only. It does **not** validate the uncommitted/current-branch behavior described here.

## How to read the result column

- **conformant** — the local implementation matches the cited official contract and has an automated contract check.
- **partial** — a correct subset exists, but a material part of the contract or parity behavior is absent.
- **not implemented** — Google supports it, but Centaur deliberately or currently does not.
- **platform gap** — Google Chat itself cannot provide the Slack-equivalent behavior or data.
- **live verification pending** — the contract is represented locally, but a real Google Workspace round trip is still required before release confidence is justified.

“Not observed” always means not observed in the retained, sanitized VPS evidence. It never means Google rejected the behavior. No raw event bodies, tokens, emails, space IDs, message IDs, attachment bytes, or signed URLs were retained or copied during the VPS audit.

## Live evidence boundary

The old VPS deployment produced the following sanitized aggregate evidence over the retained 48-hour window:

- 12 inbound events were accepted and 12 runs started; 11 completed and one failed.
- 11 answers became visible. The create-session path had 11 successes and one conflict; the conflict was a Centaur session conflict, not a Google Chat API error.
- Identity was suppressed seven times as `space_not_dm` and emitted five times.
- The ETL exercised `spaces.list`, `spaces.members.list`, and `spaces.messages.list` through the existing proxy.
- No retained Chat API failure, outbound thread/fallback failure, or raw Google request payload was available.
- There was no retained evidence for the new three-mode verifier, `spaces.setup`, reactions, DWD DM reads, `showDeleted`, upload/download, Drive export, scoped proxy mutations, or the new renderer limits.

The deployed Secret exposes `CHATBOT_API_KEY`, while the old pod had resolved its API credential already. The current local chart adds a `CENTAUR_API_KEY` fallback, but that chart change has not been rolled out. This must be checked on the next deployment.

## Release blockers, in plain language

### True blockers before calling this release “verified”

1. **The current code ran on the VPS, but not against a dedicated Workspace test app.** Native candidate images passed the isolated K3s canary, internal auth, state, policy, recovery, and cleanup gates. The remaining live gate must use a non-production app/project and owned test data to exercise all three ingress modes, message/card creation, named-space threading, DM creation/send, app and delegated history, reaction reads, upload/download, Drive export, edit/delete, and a 429/retry case. Record method/status/enum/byte-count evidence only.
2. **Source-deletion convergence has no live proof.** The official contract and current tree support `showDeleted=true` for app-auth shared-space scans and delegated DM scans. Release evidence still needs create→sync→delete→resync cases proving each tombstone removes its message, attachments, and reactions.
3. **Canary internal API wiring passed, but production-key compatibility still needs a rollout proof.** The isolated key returned the expected unauthorized and authorized-validation statuses. The production Secret's `CHATBOT_API_KEY`/`CENTAUR_API_KEY` compatibility path was not mutated or disclosed; verify it during the actual rollout before replacing the old pod.
4. **New privileged paths have no real Workspace proof.** Admin/DWD configuration and membership determine whether DM setup, DM history, reactions, upload, and Drive download actually work. Automated request-shape tests are necessary but cannot prove tenant policy. Run one allowlisted success and one denied case for each grant.
5. **Native Drive exports still lack tenant-backed proof.** Local tests model the separate 10 MB `files.export` ceiling, correct MIME/extensions, and safe oversize classification. Prove one below-limit success and above-limit rejection live; the 100 MiB binary ceiling does not apply to native exports.
6. **The 30-second ingress promise needs a live failure drill.** Stall Google lookups and downstream session startup while confirming Google receives `{}` before its deadline and the durable recovery completes later.

These are release blockers because they concern source-data reconciliation,
authentication/authorization, deployment viability, documented file limits, or
the absence of tenant-backed evidence for code that is not yet production. They are not a claim
that the locally automated request shapes are invalid.

### Not blockers unless the product scope includes them

- App Home, dynamic widget suggestions, dialog UI responses, link previews, named-space administration, membership writes, pins, reaction writes, and search are explicit unimplemented scope.
- The 100 MiB Centaur upload/download ceiling is a deliberate local restriction below Google’s 200 MB upload maximum.
- Shared StateAdapter reservations pace all same-space writes and all
  direct/aggregate reaction reads across replicas. Other independent reads use
  bounded 429 retry. Only live multi-replica load proof remains; add more
  category-specific pacing only if its metrics show sustained contention.

### Platform gaps, not defects in Centaur

- Google’s `User`, `Membership`, and `Attachment` responses do not contain the Slack-like email/size/content fields described above.
- Google Chat does not provide true response streaming or several Slack-native administrative/collaboration primitives.
- App-auth DM history and reaction listing have authorization limits that require a real user/delegated reader.
- `messageReplyOption` is a named-space feature and must not be sent for DMs/group chats.

## Conclusion

The current local implementation has strong automated conformance for the Google contracts it models. It is **not yet exhaustively live-validated**: production is on an older image, and the highest-risk new paths were not present in retained traffic. Shared-space deletion is no longer a documented auth limitation; it is a required live convergence test. Native Drive export handling models the official local contract but still needs tenant-backed below/above-limit proof. Everything else marked `live verification pending` needs tenant-backed evidence before it can move to a release claim; `not implemented` rows must remain classified as Google-native scope or actual Slack parity gaps, and platform gaps must remain explicit.
